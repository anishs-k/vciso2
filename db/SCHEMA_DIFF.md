# Database vs. workbook: every difference

Workbook: `docs/Master-Framework v13.0 Control-Framework Map.xlsx`  
Schema: `db/init/001_framework_tables.sql` (generated by `db/generate_schema.py`, which also writes this file)

Totals: 27 tables, 544 columns, 21 primary keys, 79 foreign keys, 1 unique constraint(s).

## 1. Sheets not turned into tables

- **Flow-Diagram**: diagram / UI mock-up, not a data table
- **Sample-UI**: diagram / UI mock-up, not a data table

## 2. Table structure changes

- **RCSA** is split into two tables. The sheet mixes two kinds of row: a control-area row (e.g. 100001 "IT Governance Controls") followed by its sub-control rows (1000010001 "Approved IT policies...").
  - `rcsa_control_area`: one row per area (from "Framework_ID (FK + PK)" and "Major Control Area").
  - `rcsa_sub_control`: one row per sub-control, plus a new `control_area_id` column linking it to its area (the sheet expresses this only by row order).
- **vCISO_Sub_Function_Process_Map** has no columns: the sheet only says "To be defined".
- Every table and column name is converted to lowercase snake_case (e.g. "Master-Customer-Details" -> `master_customer_details`, "Customer_Name" -> `customer_name`). The original sheet name / header is stored as a database comment on each table and column.
- **Audit columns** in every sheet: "Date of Creation" / "Date Of Creation" -> `created_at`, "Date of Update" / "Date Of Updation" -> `updated_at`, "Created BY" -> `created_by`, "Updated By" -> `updated_by`.
- Notes in brackets in a header are dropped from the name (e.g. "Office_Type (Primary/ Secondary/ Others)" -> `office_type`), except where listed in section 3.

## 7. Foreign keys added without an (FK) marker

- `customer_contract_framework_map.framework_id` -> master_framework(framework_id): Column is marked PK only, but its values are Master-Framework IDs.
- `customer_framework_role_user.framework_id` -> master_framework(framework_id): Column is marked PK only, but its values are Master-Framework IDs.
- `customer_framework_role_user.role_id` -> roles(role_id): Was License_ID (FK); now points at Roles.
- `rcsa_sub_control.control_area_id` -> rcsa_control_area(control_area_id): New column linking each sub-control to its control area (the sheet does this by row order).
- `customer_api_map.tool_id` has no (FK) marker but is part of the `tool_id` + `api_id` FK to `tool_api_map`, because API_ID (FK) can only be referenced together with Tool_ID.

## 9. Foreign keys where the target had to be chosen

The (FK) marker says a column is a foreign key but not what it points at. These were matched by meaning, not by name:

- `address_id` -> `master_customer_address_details.office_id` (values are office IDs, e.g. Cust_00101_001).
- `owner_id`, `user_id_from`, `user_id_to` -> `customer_framework_users.user_id`.
- `tool_id` + `api_id` -> `tool_api_map` together (its key is both columns).
- Everything else points at the table where the same-named column is the primary key.

## 10. Things the database adds that the sheet does not specify

- **Data types.** The sheet has none; each column is typed from its name and sample values:
  - Y/N columns -> true/false (`boolean`; Postgres accepts 'Y'/'N' when inserting).
  - Date columns -> `date`; date-time columns and the audit `created_at` / `updated_at` -> timestamp with time zone.
  - Money columns (Amount, Value) -> `numeric(15,2)`; counts, years and frequencies -> `integer`.
  - IDs follow their sample values: numeric IDs (Framework_ID, FY_ID, Clause_Control_ID, Tool_ID, API_ID...) are numbers; text IDs (Cust_00101, Role_0001...) are text.
  - A foreign-key column always gets the same type as the column it points at. Customer-API-Map.Tool_ID is therefore a number although its sample values are "Tool_1", "Tool_2".
  - Everything else -> `text`.
- **Defaults.** `created_at` is filled with the current time automatically and cannot be empty.
- **Required columns.** Primary key columns cannot be empty (a database rule).

## 11. Sample data in the sheet that the database would reject

No data is loaded, only structure. If the sample rows were imported as they are:

- **Master-Clause-Control-Map**: Clause_Control_ID repeats (10201 for 4.1, 4.2, 4.3...) and DPDPA uses text codes (DPDP-CN-01). Client builds (db/generate_client_schema.py) renumber controls 102001, 102002... in sheet order and keep the sheet's ID in `source_clause_control_id` (section 4). Inserting a row in the middle of the sheet shifts every later number, so stable IDs in the workbook are still needed before client databases are upgraded in place.
- **Customer sheets vs. Master-Clause-Control-Map**: customer sheets use 102001, 102002... for controls the master numbers 10201...; IDs must match across sheets or the foreign keys reject them.
- **Customer-Asset-Owner**: Asset_ID repeats (10201 four times for Cust_00101); looks copied from the control IDs.
- **UI-Report-Dashboard-List**: UI_ID repeats with different categories (UI_RD_0002 is both a Report and a Screen).
- **Financial Year Master**: Country_ID blank (fine now that it is not part of the key).
- **Blank key / reference values** in many rows (e.g. Customer_ID blank on continuation rows of Customer-Contract-Framework-Map and Customer-FY-Invoices); every row needs its own values.
- **Placeholder text in date / user columns** ("Future Date", "System Date", "(User ID)") are notes, not values.
